## 一、背景问题

用户调用文件引接接口时依次出现 3 类问题：

1. **接口"不存在"** —— 实际接口存在（`POST /api/yj/exec/file/exec`），是调用方式/后端未启动造成误解。
2. **XML 解析把表头当数据行入库**、文本读取乱码、XML 无 XXE 防护。
3. **达梦数据库报 `有参数未绑定: N`** —— 某行数据字段数少于建表列数，INSERT 占位符没绑全，达梦驱动严格报错。
4. **CSV 整行数据塞进一个字段** —— 协议 `separator` 未配置时默认按制表符 `\t` 拆，逗号分隔的 CSV 不拆分。

## 三、YjExecService.java 的 4 处修复

### 1. XML 解析：表头当数据行写入 + 字段名不做建表列

**文件位置**：`parseXmlFile`、`execFile`

- 原逻辑：第一个 `<record>` 的字段名（`id`、`name`…）被当作第 1 行数据插入表，反直觉。
- 修复后：
  - 表头（字段名）**不再入库**，只入库数据行；
  - 返回 `XmlParseResult`（字段名 + 数据行）；
  - 协议未配置列定义时，用第一个 `<record>` 的子元素标签名**自动建表列**（不再生成 `COL_1` 无名列）。

### 2. 文本/CSV 读取编码

**文件位置**：`parseTextFile`、`detectCharset`（新增）

- 原逻辑：`new FileReader(file)` 使用系统默认编码（中文 Windows 为 GBK），UTF-8 文件乱码。
- 修复后：`Files.readAllBytes` + `detectCharset` 自动探测 —— UTF-8（含 BOM）优先，严格解码失败回退 GBK。

### 3. 插入行补齐占位符（修复达梦 `有参数未绑定`）

**文件位置**：`execFile` 批量插入循环

- 原逻辑：`for (int i = 0; i < colCount && i < row.length; i++)` —— 行字段数少于 `colCount` 时占位符未绑定，达梦驱动报 `有参数未绑定: N`。
- 修复后：每行绑定全部 `colCount` 个占位符，缺失字段补 null。

### 4. 分隔符自动探测

**文件位置**：`execFile`、`detectSeparator`（新增）、`parseJumpRows`（抽取）

- 原逻辑：协议 `separator` 未配置时默认按 `\t` 拆，逗号分隔的 CSV 整行进一个字段。
- 修复后：协议未显式配置分隔符时，按样例行（最多 20 行）统计逗号 `,`/制表符 `\t`/分号 `;`/竖线 `|` 的拆分结果，选取**列数一致且最多**的分隔符，探测不到回退 `\t`。已用 Node 模拟验证各类输入。

## 六、注意事项 / 遗留问题

1. **不要传 XLS/XLSX 二进制文件**：uploads 里的 `新建 XLS 工作表.csv` 实际是 OLE2/XLS 二进制（魔数 `d0cf11e0`），文本解析读它必乱码。测 CSV/XML 必须用真正的文本文件。
2. **CSV 表头不会自动跳过**：表头会被当第一条数据入库。不想入库就在文件引接配置里设 `jumpRow=1`。
3. **目标表已存在时是清空重插**（DELETE + INSERT），不会自动改表结构。
4. **XML 要求**：标签必须是 `<record>`（大小写敏感），字段取直接子元素；已开启 XXE 防护，**不允许 DOCTYPE 声明**。
5. **分隔符探测是保守的**：若某字段值内部含分隔符（如 `1,000`）导致各行拆分列数不一致，会回退到 `\t`；此类场景建议在协议里显式配置 `separator`。
6. 字段数缺失时自动补 null（不再报错），但补出来的是空值，列数/顺序不一致的问题仍需在文件或协议侧保证。
